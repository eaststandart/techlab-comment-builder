# Конструктор комментариев TechLab

Этот репозиторий выполняет роль изолированного буферного шлюза для приема, проверки и подготовки комментариев с фотографиями и видеоматериалами. Он получает манифесты и вложения из веб-формы или Obsidian, обрабатывает медиаматериалы и передает готовые комплекты в основной репозиторий сайта [eaststandart.github.io](https://github.com/eaststandart/eaststandart.github.io) для публикации в GitHub Discussions.

### Зачем создан этот репозиторий

1. **Изоляция и безопасность:** прием пользовательских материалов выполняется отдельно от основного репозитория сайта.
2. **Подготовка медиаматериалов:** файлы проверяются, переименовываются и оптимизируются до передачи на публикацию.
3. **Управление публикацией:** поле `published` определяет, сохранить черновик, передать комплект на обработку или удалить его.
4. **Последовательная передача:** единый диспетчер обрабатывает комплекты по очереди и контролирует освобождение выходного шлюза `_output/`.

### Как это работает (Краткая логика системы)

Система построена на GitHub Actions и скриптах Python. Обработка выполняется последовательно:

1. Автор отправляет Markdown-манифест и связанные с ним вложения в папку `_input/` через веб-форму или Obsidian.
2. Workflow `comment_builder.yml` запускает главный диспетчер `comment_builder.py`.
3. Диспетчер синхронизирует репозиторий и проверяет, свободна ли папка `_output/`. Если предыдущий комплект еще не забран основным сайтом, диспетчер ожидает ее очистки.
4. Модуль `manifest_processor.py` предварительно проверяет манифесты и удаляет комплекты, помеченные для удаления или содержащие некорректные данные.
5. Модуль `manifest-analyzer.py` проверяет дату и вложения, стандартизирует имена файлов, запускает компрессоры и готовит комплект в `_output/`.
6. Диспетчер сохраняет комплект в Git, отправляет основному сайту сигнал `comment-notify` и ожидает очистки `_output/`. После этого начинается обработка следующего комплекта.

*Примечание: параллельные запуски workflow блокируются настройкой concurrency. Дата публикации проверяется по времени Владивостока (UTC+10).*

#### Назначение директорий

* **`.github/workflows/`** — сценарии GitHub Actions. Управляют запуском главного диспетчера при поступлении Markdown-манифеста в `_input/`.
* **`_actions/`** — Python-модули. Содержат логику управления очередью, предварительной проверки манифестов, анализа комплектов, переименования и сжатия медиаматериалов.
* **`_input/`** — входная папка для Markdown-манифестов и связанных с ними фотографий и видео.
* **`_output/`** — выходной шлюз для подготовленного комплекта, ожидающего передачи основному сайту.
* **`_published/`** — служебная папка с образцом манифеста и тестовыми файлами для проверки обработки.

## ЧАСТЬ 2: Клиентский интерфейс и публикация (`eaststandart.github.io`)

Основной сайт отвечает за интерфейс создания комментариев, прием материалов из веб-формы, получение готового комплекта из буферного репозитория и публикацию текста и медиаматериалов в GitHub Discussions.

### Два способа отправки

* **Веб-форма:** автор заполняет форму на сайте и отправляет манифест с вложениями в `_input/` репозитория конструктора комментариев.
* **Obsidian:** автор подготавливает Markdown-манифест и связанные файлы, после чего отправляет комплект в репозиторий обычным Git push.

### Передача готового комплекта

После подготовки комплекта диспетчер сохраняет его в `_output/`, фиксирует изменения в Git и отправляет событие `comment-notify` в репозиторий основного сайта. Дальнейшее получение и публикация комплекта выполняются автоматизацией `eaststandart.github.io`.

## Последовательность обработки

* При поступлении Markdown-манифеста в `_input/` запускается workflow `comment_builder.yml`.
* Главный диспетчер проверяет состояние `_output/` и при необходимости ожидает освобождения шлюза.
* Предварительная обработка определяет, какие манифесты и вложения должны остаться во входной папке.
* Манифесты с `published: false` сохраняются как черновики.
* Манифесты с `published: delete` и некорректные манифесты удаляются вместе с относящимися к ним файлами, если эти файлы не используются другими сохраняемыми манифестами.
* Манифесты с `published: true` передаются анализатору для проверки даты и комплектности вложений.
* Анализатор стандартизирует имена файлов, запускает обработку фотографий и видео и передает подготовленный комплект в `_output/`.
* После Git-коммита и уведомления основного сайта диспетчер ожидает очистки `_output/` и только затем переходит к следующему комплекту.

## Обработка ошибок

При обработке медиаматериалов используются два отдельных статуса:

* **`FILE_CORRUPTED`** — обнаружены признаки повреждения файла. Текущий процесс немедленно останавливается без повторных попыток; в статусе указываются имя файла и причина.
* **`RETRY`** — произошла другая ошибка обработки. Выполняются до четырех попыток с интервалами 60, 180 и 300 секунд. Причина каждого сбоя сохраняется в журнале. Если все попытки исчерпаны, процесс завершается с ошибкой.

Комплект, который не прошел обработку, не передается в `_output/`.

## Дата публикации

Анализатор сравнивает значение `date` в формате `YYYY-MM-DD` с текущей датой по Владивостоку.

* **Будущая дата:** комплект остается во входной папке до следующего запуска обработки.
* **Сегодняшняя или прошедшая дата:** комплект допускается к дальнейшей проверке и обработке.
* **Отсутствующая или некорректная дата:** комплект пропускается с сообщением в журнале.

Запуск выполняется по событию `push` Markdown-манифеста в `_input/`. Отдельного планировщика, который автоматически запускает обработку в момент наступления даты, нет.
