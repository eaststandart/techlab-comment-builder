# techlab-media-content

# 🗺️ Дорожная карта проекта: Мультиканальный медиа-шлюз (TechLab Media Content)

Этот документ является сквозным техническим регламентом и памяткой по реализации, архитектуре и эксплуатации изолированной подсистемы автоматической публикации медиа-материалов в **GitHub Discussions** Творческой лаборатории.

---

## 🎯 1. Назначение и философия проекта

Проект создан для кардинального упрощения и ускорения документирования учебного процесса. Он решает три ключевые проблемы:
1. **Изоляция и безопасность:** Преподаватели имеют доступ на запись только в выделенный репозиторий-склад `techlab-media-content`. Доступ к коду сайта (`eaststandart.github.io`) и базе расписания для них полностью закрыт.
2. **Оптимизация ресурсов:** Автоматическое серверное сжатие тяжелых медиафайлов (до 10-15 МБ) в легкий современный формат **WebP** (для фото) и оптимизированный **MP4** (для видео). Это обеспечивает мгновенную загрузку страниц у родителей.
3. **Чистота репозиториев:** Медиафайлы физически загружаются и хранятся **внутри облачного хранилища аттачментов Дискуссий GitHub** (`user-attachments`), а не засоряют папки сайта или базы данных.

---

## 🏗️ 2. Архитектура и структура папок

Система развернута в изолированном репозитории **`techlab-media-content`** и работает по проверенному модульному принципу конвейера «Вход ➔ Диспетчер ➔ Выход».

### Структура репозитория
```text
[techlab-media-content]
├── 📂 .github/workflows/       # Конвейеры автоматизации (GitHub Actions)
│   └── media-processor.yml     # Главный триггер серверной обработки пакетов
├── 📂 _actions/                # Серверная логика на языке Python
│   ├── media_dispatcher.py     # Центральный диспетчер очереди пакетов
│   ├── media_compressor.py     # Модуль валидации, сжатия графики и видео
│   └── media_publisher.py      # Модуль интеграции с GitHub CLI (gh)
├── 📁 _input/                  # Единый буфер шлюза (Markdown-манифесты и сырые файлы)
└── 📁 _output/                 # Выходной шлюз (сессионные JSON-логи результатов)
```

---

## ⚙️ 3. Логика работы конвейера обработки

Робот на сервере функционирует по строгому алгоритму, полностью исключающему кашу или потерю данных при одновременной работе нескольких преподавателей:

1. **Сканирование Входа:** По сигналу `push` робот заходит в папку `_input/` и ищет файлы с расширением `.md`. Все остальные файлы (картинки, видео), не привязанные к манифестам, на этом этапе игнорируются.
2. **Контроль комплектности:** Для каждого найденного `.md` файла робот парсит его текст, составляет список упомянутых картинок/видео и проверяет их физическое наличие в папке `_input/`. 
   * *Железное правило:* Если в тексте указан файл `photo1.jpg`, а в папку его забыли загрузить — робот **останавливает обработку этого пакета** и пишет ошибку в лог, защищая Дискуссии от битых постов.
3. **Обходной фильтр WebP:** Если файл уже имеет расширение `.webp`, модуль сжатия полностью пропускает его, отправляя в публикатор «как есть», экономя процессорное время сервера.
4. **Магия загрузки (GitHub CLI):** Робот берет сжатый файл и через консольную утилиту `gh` имитирует ручное прикрепление файла к Дискуссии. В ответ Гитхаб выдает вечную прямую ссылку вида `https://github.com...`.
5. **Финальная сборка и зачистка:** Робот заменяет локальные имена файлов в тексте заметки на полученные интернет-ссылки, публикует один красивый итоговый пост в Дискуссии и **полностью стирает** отработанный `.md` и картинки из папки `_input/`.

## 👥 4. Два сценария эксплуатации (Как с этим работать)

### Поток А: Работа автора через Obsidian (Дома / Отложенный отбор)
* **Процесс:** Вы открываете Obsidian, создаете в папке `_input` заметку `отчет.md`, прописываете YAML-шапку и перетаскиваете файлы из проводника. 
* **Шаблон заметки:**

```markdown
---
discussion_number: 38      # Номер целевой дискуссии на сайте
date: "2026-10-24"         # Дата (робот сам вычислит день недели)
teacher: "TechLab"         # Подпись автора
---
### 🚀 Заголовок отчета в Obsidian
Здесь идет ваш свободный текст для родителей.

![[photo1.jpg]]
<!-- #techlab-baranova-liza -->
```

* **Действие:** Делаете стандартный `git push` (через плагин Obsidian Git или PowerShell). Робот сам всё сделает, опубликует и очистит папку.

🎛 4.1. Управление жизненным циклом пакета (CMS-логика)

Чтобы автор всегда имел историю публикаций, мог планировать посты заранее и защищать черновики от случайного выпуска, робот обрабатывает Front Matter свойства .md файла по следующим правилам:
1. Контроль флага видимости (published):
	• Если в шапке указано published: false (или status: draft), робот полностью игнорирует этот файл. Это ваш личный черновик, который можно спокойно хранить и дописывать в Obsidian.
	• Публикация начнется только тогда, когда вы измените флаг на published: true.
2. Контроль времени (Отложенная публикация):
	• Робот сравнивает дату из поля date: "YYYY-MM-DD" с текущей датой сервера GitHub Actions (по Владивостоку).
	• Если дата будущая (например, занятие в субботу, а вы загрузили отчет в пятницу), робот пропускает этот пакет до наступления указанного дня.
	• Если дата текущая или прошлая, пакет немедленно улетает в работу.
3. Архивация вместо удаления:
	• После успешной отправки поста в Дискуссии робот не стирает .md файл. Он меняет в его шапке значение published: true на исходную дату публикации (или добавляет поле published_at: 2026-10-23) для истории.
	• Робот автоматически переносит этот измененный .md файл из папки _input/ в архивную папку _processed/.
	• Важно: Оригинальные тяжелые картинки из _input/ после отправки в облако Гитхаба всё равно удаляются, чтобы не раздувать репозиторий (только ссылки на них в md файле изменять на ссылки на дискусии и еще файл переименовывать в типа - дата_discussion_номер_имяпрепода). В архиве _processed/ остается только чистый текстовый отчет.

• Если это новый пост: Робот переименует его в: 2026-10-24_discussion_38_TechLab.md
• Если это перезапись старого поста: Робот переименует его в: 2026-10-24_discussion_38_comment_1867726_TechLab.md

### Поток Б: Работа преподавателей через Веб-форму (На ходу со смартфона)
* Преподаватели не имеют прав соавторства и не видят этот репозиторий.
* На странице Журнала они видят простую форму: `Дата` ➔ `Текст` ➔ `Кнопка выбора файлов из галереи`.
* При нажатии кнопки «Опубликовать» JavaScript на сайте, используя выделенный технический токен, сам кодирует файлы в Base64, автоматически генерирует аналогичный `.md` манифест и выплевывает всю пачку в папку `_input/` через GitHub API за 3 секунды.
