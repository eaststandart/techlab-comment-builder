# techlab-media-content

# 🗺️ Дорожная карта проекта: Конструктор комментариев

Этот документ является сквозным техническим регламентом и памяткой по реализации, архитектуре и эксплуатации проекта.

---

## 🎯 1. Назначение и философия проекта

Проект создан для кардинального упрощения и ускорения документирования учебного процесса. Он решает три ключевые задачи:
1. **Изоляция и безопасность:** Преподаватели имеют доступ на запись только в выделенный репозиторий-склад `techlab-media-content`.
2. **Оптимизация ресурсов:** Автоматическое серверное сжатие тяжелых медиафайлов (до 10-15 МБ) в легкий современный формат.
3. **Чистота репозиториев:** Медиафайлы физически загружаются и хранятся внутри облачного хранилища аттачментов GitHub Discussions.

---

## 🏗️ 2. Архитектура и структура папок

Система развернута в изолированном репозитории **`techlab-media-content`** и работает по проверенному модульному принципу.

### Структура репозитория
```text
[techlab-media-content]
├── 📂 .github/workflows/       # Конвейеры автоматизации (GitHub Actions)
│   └── media-processor.yml     # Главный триггер серверной обработки пакетов
├── 📂 _actions/                # Серверная логика на языке Python
│   ├── media_dispatcher.py     # Центральный диспетчер очереди пакетов
│   ├── media_compressor.py     # Модуль валидации, сжатия графики и видео
│   └── media_publisher.py      # Модуль интеграции с GitHub CLI (gh)
├── 📁 _input/                  # Единый буфер шлюза (Markdown-манифесты и сырые файлы)
└── 📁 _output/                 # Выходной шлюз (сессионные JSON-логи результатов)
```

---

## ⚙️ 3. Логика работы конвейера обработки

Робот на сервере функционирует по строгому алгоритму, полностью исключающему кашу или потерю данных при обработке.

1. **Сканирование Входа:** По сигналу `push` робот заходит в папку `_input/` и ищет файлы с расширением `.md`. Все остальные типы игнорируются.
2. **Контроль комплектности:** Для каждого найденного `.md` файла робот парсит его текст, составляет список упомянутых файлов и сверяет их с реальным содержимым папки.
   * *Железное правило:* Если в тексте указан файл `photo1.jpg`, а в папку его забыли загрузить — робот **останавливает обработку** и пишет предупреждение в лог.
3. **Обходной фильтр WebP:** Если файл уже имеет расширение `.webp`, модуль сжатия полностью пропускает его, отправляя в очередь как готовый к публикации объект.
4. **Магия загрузки (GitHub CLI):** Робот берет сжатый файл и через консольную утилиту `gh` имитирует ручное прикрепление в обсуждение на сайте.
5. **Финальная сборка и зачистка:** Робот заменяет локальные имена файлов в тексте заметки на полученные интеграционные идентификаторы, создает финальный markdown и обновляет архив логов.

## 👥 4. Два сценария эксплуатации (Как с этим работать)

### Поток А: Работа автора через Obsidian (Дома / Отложенный отбор)
* **Процесс:** Вы открываете Obsidian, создаете в папке `_input` заметку `отчет.md`, прописываете YAML-шапку и перетаскиваете в нее фото/видео.
* **Шаблон заметки:**

```markdown
---
discussion_number: 38      # Номер целевой дискуссии на сайте
date: "2026-10-24"         # Дата (робот сам вычислит день недели)
teacher: "TechLab"         # Подпись автора
---
### 🚀 Заголовок отчета в Obsidian
Здесь идет ваш свободный текст для родителей.

![[photo1.jpg]]
<!-- #techlab-baranova-liza -->
```

* **Действие:** Делаете стандартный `git push` (через плагин Obsidian Git или PowerShell). Робот сам всё сделает, опубликует и заархивирует пакет.

🎛 4.1. Управление жизненным циклом пакета (CMS-логика)

Чтобы автор всегда имел историю публикаций, мог планировать посты заранее и защищать черновики от случайного выкладывания, применяются правила:
1. Контроль флага видимости (published):
	• Если в шапке указано `published: false` (или `status: draft`), робот полностью игнорирует этот файл. Это ваш личный черновик.
	• Публикация начнется только тогда, когда вы измените флаг на `published: true`.
2. Контроль времени (Отложенная публикация):
	• Робот сравнивает дату из поля `date: "YYYY-MM-DD"` с текущей датой сервера GitHub Actions.
	• Если дата будущая, робот пропускает этот пакет до наступления срока.
	• Если дата текущая или прошлая, пакет немедленно улетает в работу.
3. Архивация вместо удаления:
	• После успешной отправки поста робот меняет в шапке значение `published: true` на `archived: true`.
	• Робот автоматически переносит этот измененный `.md` файл из папки `_input/` в архивную папку `_processed/`.
	• Важно: Оригинальные тяжелые картинки из `_input/` после отправки в облако всё равно удаляются, чтобы освободить место.

• Если это новый пост: Робот переименует его в: `2026-10-24_discussion_38_TechLab.md`
• Если это перезапись старого поста: Робот переименует его в: `2026-10-24_discussion_38_comment_1867726_TechLab.md`

### Поток Б: Работа преподавателей через Веб-форму (На ходу со смартфона)
* Преподаватели не имеют прав соавторства и не видят этот репозиторий.
* На странице Журнала они видят простую форму: `Дата` ➔ `Текст` ➔ `Кнопка выбора файлов из галереи`.
* При нажатии кнопки «Опубликовать» JavaScript на сайте, используя выделенный технический токен, сам кодирует форму и отправляет пакет в медиа-шлюз.

# 🚀 Документация CMS-модулей автоматизации: Медиа-Шлюз и Боевой Сайт

Данная спецификация фиксирует финальную архитектуру сквозной публикации медиа-отчетов TechLab, разделенную по двум независимым репозиториям.

---

## 📁 ЧАСТЬ I. МЕДИА-РЕПОЗИТОРИЙ (techlab-media-content)

Медиа-репозиторий выполняет роль изолированного буфера (шлюза). Сюда через API поступают сырые тяжелые файлы, затем обрабатываются роботами и превращаются в нормальные веб-объекты.

### 📐 1. Стандарт именования сессионных файлов (Паспорт черновика)
Чтобы исключить наложение файлов от разных преподавателей в один день, каждый пакет получает уникальный сессионный идентификатор.
Все файлы сессии в папке `_input/` маркируются единым префиксом:
`{YYYY-MM-DD}-{timestamp}_{teacher}_[тип]_[индекс].[расширение]`

*Пример:* `2026-10-25-1792762529_TechLab_photo_01.jpg`

---

### ⚙️ 2. Серверный модуль точечной зачистки `media_cleaner.py`
Для реализации идеи безопасной синхронизации черновиков в конвейер шлюза внедряется новый обработчик.

#### 🔄 Логика работы робота:
1. **Перехват семафора:** Робот просыпается, когда в `_input/` залетает манифест с флагом `status: on` во Front Matter.
2. **Изоляция зоны ответственности:** Робот считывает из манифеста `date`, `timestamp` и `teacher` и формирует строгую маску файлов.
3. **Поиск файлов-сирот:**
    * С помощью `os.listdir("_input")` робот собирает список всех файлов на диске, принадлежащих только этой конкретной сессии.
    * Робот парсит текст текущего `.md` файла и собирает список ссылок, которые остались на экране у учителя.
    * Если файл с диска отсутствует в тексте манифеста, он считается мусором и удаляется.
4. **Снятие блокировки (Разблокировка формы):** После удаления мусора робот переписывает Front Matter манифеста, отмечая пакет как готовый к дальнейшей обработке.

---

### ⚙️ 3. Серверные модули сжатия и переименования
После зачистки мусора управление передается основным модулям ядра:
* **`media_compressor_photo.py`**: Уменьшает оставшиеся фото до стандарта HD (**1280x720**), пережимает в `.webp` с качеством 80 и удаляет исходник.
* **`media_compressor_video.py`**: Запускает двойной тест FFmpeg (кодек видео `libvpx-vp9`, аудио `libvorbis`, размер 720x480, 30fps). Первый прогон тестирует пригодность, второй — финальное сжатие.
* **Перенумерация:** Робот сканирует финальный текст сверху вниз и затягивает «дыры» от удаленных блоков, переиндексируя медиа-блоки.

## 🌐 ЧАСТЬ II. СТОРОНА БОЕВОГО САЙТА (eaststandart.github.io)

Репозиторий сайта отвечает за отображение унифицированной формы, отправку тяжелых файлов по API и финальную публикацию комментариев в GitHub Discussions.

### 📱 1. Работа Унифицированной Формы ввода (v10)
Форма полностью оптимизирована под мобильные экраны и разбита на 4 логические зоны:

1. **Управляющая CMS-шапка (Три линии):**
    * *Линия 1:* `Дата: [YYYY-MM-DD]` (всегда на экране).
    * *Линия 2:* Поле ввода `Дискуссия: [№-коммит]` + чекбоксы статуса.
    * *Линия 3:* Выпадающий список черновиков.
2. **Контекст отчета (Блок 2):** Три поля ввода внутри одной карточки (*Заголовок комментария*, *Описание*, *Теги*).
3. **Блочный конструктор (📸 Фото / 🎥 Видео):** Позволяет кнопками `+ Добавить блок` плодить неограниченное количество медиа-элементов.
4. **Кнопка Контроля:** Динамически меняет текст в зависимости от статуса публикации.

---

### 🤖 2. Что нужно сделать на стороне сайта (Робот-Публикатор)

При нажатии кнопки «Создать комментарий» JavaScript отправляет файлы в шлюз, а на стороне сайта просыпается workflow-публикатор.

1. **Скачивание готового пакета:** Как только от медиа-шлюза прилетает сигнал `repository_dispatch`, робот сайта обращается к конечной точке API.
2. **Публикация в GitHub Discussions:**
    * Робот сайта считывает из Front Matter номер обсуждения (`discussion_number`).
    * С помощью официального GraphQL API Гитхаба робот отправляет текст отчета, ссылки на готовые `.webp`/`.webm` и подтверждает публикацию.
3. **Архивация и Очистка шлюза:** После успешного добавления комментария на сайт робот отправляет POST-запрос в медиа-шлюз, чтобы там закрылась сессия и удалились временные файлы.
