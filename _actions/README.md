## Управляющие скрипты (Python)

В каталоге `_actions/` сосредоточена логика управления очередью комплектов комментариев, предварительной проверки манифестов, анализа вложений и подготовки медиаматериалов к публикации.

### Структура папки

~~~text
[techlab-comment-builder]
└── _actions/
    ├── comment_builder.py          # Главный диспетчер буферного шлюза
    ├── comment_processor.py        # Последовательный запуск этапов обработки
    ├── manifest_processor.py       # Предварительная проверка и очистка _input
    ├── manifest-analyzer.py        # Анализ даты, вложений и подготовка комплекта
    ├── comment_renamer.py          # Стандартизация имен файлов
    ├── media_compressor_photo.py   # Оптимизация фотографий в WebP
    └── media_compressor_video.py   # Оптимизация видео в WebM
~~~

### Основные модули буферного шлюза

* **`comment_builder.py` (Главный диспетчер буферного шлюза)**
  * **Назначение:** Управляет последовательной обработкой комплектов, синхронизацией репозитория, Git-коммитами и передачей готовых данных основному сайту.
  * **Логика работы:** Проверяет состояние `_output/`, при необходимости ожидает удаления предыдущего комплекта, запускает предварительную обработку и анализатор. После успешной подготовки сохраняет комплект в Git, отправляет событие `comment-notify` в основной репозиторий и ожидает освобождения выходного шлюза.

* **`comment_processor.py` (Модуль последовательного запуска обработки)**
  * **Назначение:** Обеспечивает запуск предварительного обработчика и анализатора с передачей результата главному диспетчеру.
  * **Логика работы:** Сначала запускает `manifest_processor.py`, затем `manifest-analyzer.py`. Вывод анализатора передается в журнал в реальном времени. Для одной попытки анализатора установлен тайм-аут 15 минут; при превышении времени процесс и его дочерние процессы завершаются.

### Модули предварительной обработки и анализа

* **`manifest_processor.py` (Модуль предварительной проверки манифестов)**
  * **Назначение:** Определяет, какие манифесты и связанные файлы должны оставаться во входной папке до запуска анализатора.
  * **Логика работы:** Читает Front Matter и извлекает ссылки на вложения из Markdown-ссылок и Obsidian WikiLink. Манифесты с `published: false` сохраняются как черновики, `published: true` передаются анализатору, `published: delete` удаляются вместе с неиспользуемыми вложениями. Некорректные манифесты также удаляются. Файлы, используемые другими сохраняемыми манифестами, не удаляются.

* **`manifest-analyzer.py` (Модуль анализа и подготовки медиакомплекта)**
  * **Назначение:** Проверяет готовность комплекта к публикации и координирует обработку его вложений.
  * **Логика работы:** Проверяет метаданные манифеста, дату публикации по времени Владивостока и наличие связанных файлов. Вызывает `comment_renamer.py` для стандартизации имен, затем соответствующие компрессоры. При успешной обработке переносит подготовленный комплект в `_output/` и возвращает диспетчеру финальный статус.

### Специализированные подмодули обработки файлов

* **`comment_renamer.py` (Модуль стандартизации имен файлов)**
  * **Назначение:** Приводит имена вложений к единому формату, используемому при публикации комментариев.
  * **Логика работы:** Формирует общий префикс из даты, временной метки, номера обсуждения, идентификатора комментария (если он указан) и автора. Присваивает фотографиям и видео последовательные двузначные номера в порядке появления вложений в тексте манифеста, обновляя ссылки внутри текста.

* **`media_compressor_photo.py` (Модуль оптимизации фотографий)**
  * **Назначение:** Проверяет изображения и подготавливает их в формате WebP.
  * **Логика работы:** Применяет коррекцию ориентации по EXIF, при необходимости уменьшает изображение до ограничений 1280×720 и сохраняет WebP с качеством 75. Файл WebP, который уже соответствует ограничениям, не перекодируется. Результат записывается во временный файл и заменяет целевой только после успешного сохранения.

* **`media_compressor_video.py` (Модуль оптимизации видеоматериалов)**
  * **Назначение:** Проверяет видеопоток и подготавливает видео в формате WebM.
  * **Логика работы:** WebM, соответствующий ограничению 720 пикселей по большей стороне, сохраняется без повторного кодирования. Остальные видео обрабатываются двумя режимами FFmpeg: CRF 25 и битрейт 700 kbps. В `_output/` передается вариант меньшего размера.

### Результаты обработки медиаматериалов

Анализатор возвращает диспетчеру один из трех статусов:

* **`SUCCESS` (Успешная обработка)**
  * **Логика работы:** Комплект успешно подготовлен и перенесен в `_output/`. Диспетчер фиксирует готовый комплект в Git и запускает `comment-notify`.

* **`FILE_CORRUPTED` (Поврежденный файл)**
  * **Логика работы:** При явных признаках повреждения исходного файла обработка немедленно прекращается. Повторные попытки не выполняются. В сообщении указываются имя файла и причина сбоя.

* **`RETRY` (Повторная попытка обработки)**
  * **Логика работы:** Для остальных ошибок диспетчер выполняет до четырех запусков анализатора. Интервалы между повторными попытками составляют 60, 180 и 300 секунд. Причина сбоя выводится в журнал. После исчерпания попыток процесс завершается с ошибкой, а комплект не передается в `_output/`.

### Контур сквозной цепочки модулей

Схема показывает порядок вызова Python-модулей и переходы между этапами обработки. Повторный запуск выполняется только для `manifest-analyzer.py`.

                                            │
                                            │
                                            ▼
                        ┌──── Обработка вложений по типу файла
                        │      
          ┌─────────────┴──────────────┐

### Примечания к последовательности

* `comment_builder.py` вызывает функции запуска из `comment_processor.py`: сначала для `manifest_processor.py`, затем для `manifest-analyzer.py`.
* `manifest-analyzer.py` вызывает `comment_renamer.py`, а затем обрабатывает вложения в порядке их перечисления в комплекте. Для фотографии вызывается фотокомпрессор, для видео — видеокомпрессор; эти ветви не являются параллельными.
* При статусе `FILE_CORRUPTED` диспетчер завершает текущий запуск без повторов. При `RETRY` повторно запускается только анализатор; после четырех неудачных запусков комплект не передается в `_output/`.
* После успешной подготовки диспетчер фиксирует комплект в Git и отправляет сигнал `comment-notify`. Следующий комплект не обрабатывается до очистки `_output/` основным сайтом.
